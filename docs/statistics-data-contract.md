# Statistics Data Contract

## 1. Current source

Legacy Statistics reads `website/old-site/expeditions/expeditions.geojson`, a 13,719,394-byte GeoJSON `FeatureCollection` containing 524 `LineString` features and 22 properties per feature.

Only `nr`, `date`, `name`, and `got` are consumed. Geometry and the remaining 18 properties do not contribute to the table.

## 2. Current browser-side processing

The browser fetches GeoJSON, parses dates and GOT values, constructs a year range, assigns records to 36 ten-day periods per year, calculates cumulative yearly totals, blanks future current-year periods, builds tooltip records, rounds values, assigns color bands, and creates the table.

These are stable domain and build operations rather than runtime browser responsibilities.

## 3. Proposed source

Python should generate a dedicated normalized artifact:

```text
src/data/generated/statistics.json
```

The existing Expeditions GeoJSON remains authoritative for the current legacy page and remains unchanged. The new artifact should contain only normalized Statistics records, precomputed period series, and summaries.

## 4. Architecture decision

### Option A — Direct GeoJSON

Advantages:

- no second generated artifact;
- no initial Python generator change;
- one source file.

Disadvantages:

- Astro must read and validate 13.7 MB of geometry;
- 18 of 22 properties and all coordinates are unused;
- the Statistics contract remains coupled to map schema evolution;
- domain calculations move only from browser to Astro rather than to their proper owner;
- isolated contract testing is harder.

### Option B — Dedicated Statistics JSON

Advantages:

- small, purpose-specific input;
- explicit versioned schema;
- no map geometry;
- Python owns normalization, validation, totals, and deterministic sorting;
- Astro receives ready-to-render data;
- contract tests can be isolated from GeoJSON presentation concerns;
- future schema evolution does not require Statistics to mirror Expeditions.

Costs:

- one additional generated artifact;
- controlled duplication of four normalized source fields;
- Python generator work is required in Sprint 11.

### Decision

Select **Option B: dedicated normalized Statistics JSON generated by Python**. The large reduction in coupling and payload, clear calculation ownership, and stronger validation outweigh the small amount of controlled duplication.

```json
{

  "generatedAt": "2026-06-21T21:05:43Z",
  "records": [
    {
      "id": "1501",
      "date": "2015-05-01",
      "name": "Ostra Hora",
      "gotPoints": 25.42
    }
  ],
  "series": [

          "cumulativeGotPoints": 0,

        }
```

The example uses real source values but intentionally omits the remainder of the dataset.

## 6. TypeScript representation

`src/data/statistics.types.ts` defines:

- `StatisticsRecord`
- `StatisticsPeriod`
- `StatisticsYearSeries`
- `StatisticsYearSummary`
- `StatisticsSummary`
- `StatisticsDataset`

The types expose no GeoJSON geometry and use no `any`.

## 7. Required fields

Dataset:

- `schemaVersion`
- `generatedAt`
- `records`
- `series`
- `summary`

Record:

- `id`
- `date`
- `name`
- `gotPoints`

Period:

- `month`
- `segment`
- `cumulativeGotPoints`
- `recordIds`

Summary:

- record count;
- total GOT points;
- first and last dates;
- yearly record counts and totals.

## 8. Optional fields

The initial contract has no optional fields. Current source coverage is complete for all four normalized record values.

Adding optional fields later requires an explicit schema-version decision. Map-only or speculative values must not be added merely because they exist in GeoJSON.

## 9. Units

- `gotPoints`: GOT points.
- `cumulativeGotPoints`: GOT points accumulated within one calendar year.
- `totalGotPoints`: GOT points.
- `recordCount`: dimensionless count.
- `month`: integer 1–12.
- `segment`: `1` for days 1–10, `2` for 11–20, `3` for 21 through month end.

No distance, elevation, duration, or coordinate unit is part of this contract.

## 10. Null policy

Source records must not contain null record fields.

`cumulativeGotPoints` is the only nullable value. `null` means a future period that was not yet reached at generation time. It does not mean zero, missing data, or a validation failure.

Empty strings are invalid for `id`, `date`, and `name`. Invalid records must fail generation rather than receive silent fallbacks.

## 11. Date and timestamp formats

- Record dates: valid Gregorian dates formatted `YYYY-MM-DD`.
- `generatedAt`: UTC RFC 3339 timestamp.
- Future-period evaluation: based on the UTC date documented by the generator, not an end user's browser clock.

Date strings are compared and sorted only after validation.

## 12. Number format and precision

JSON stores native finite numbers with a dot as the JSON decimal separator.

- Source GOT points retain their available precision.
- Period and summary totals should be deterministically rounded to two decimal places after decimal-safe summation.
- Main cumulative table cells display whole points to preserve current behavior.
- Detail values display two decimal places.
- Astro may use the Polish locale for rendered values; no locale switcher is planned.

NaN, Infinity, negative GOT points, and numeric strings are invalid.

## 13. Identifier policy

`StatisticsRecord.id` derives from `Feature.properties.nr`.

It must be:

- a non-empty trimmed string;
- unique across the dataset;
- stable between generations;
- preserved as a string, including any leading zeros.

Period `recordIds` must reference existing record IDs exactly once in the period matching each record date.

## 14. Sorting assumptions

Python produces deterministic order:

1. records by `date` ascending;
2. equal-date records by `id` using ordinal string comparison;
3. yearly series by `year` ascending;
4. periods by `month` ascending and then `segment` ascending;
5. period `recordIds` in normalized record order;
6. yearly summaries by `year` ascending.

Astro must not silently re-sort domain data. It may choose a static visual column direction only if documented and tested.

## 15. Summary calculations

Python calculates:

- total normalized record count;
- total GOT points;
- first and last dates;
- record count and GOT total per year;
- 36 periods per included year;
- period membership;
- cumulative yearly GOT at every period;
- future-period null values.

The current 524-record source yields 10,349.23 total GOT points across 12 years.

## 16. Validation responsibilities

Contract validation must verify:

- schema version;
- valid JSON structure;
- required keys and exact types;
- unique IDs;
- valid dates;
- finite non-negative GOT values;
- month and segment ranges;
- exactly 36 ordered periods per year;
- record-reference integrity;
- one period membership per record;
- deterministic ordering;
- totals and counts recalculated from records;
- null values only for permitted future periods.

The Sprint 10 Node validator proves the current GeoJSON contains enough information to build the contract. The production validator should validate the generated Statistics JSON itself.

## 17. Python responsibilities

Python owns:

- reading authoritative source data;
- source and domain validation;
- normalized field names;
- decimal-safe GOT summation;
- date parsing and period assignment;
- cumulative totals;
- summaries;
- future-period boundaries;
- deterministic sorting;
- schema version and generation timestamp;
- deterministic UTF-8 JSON output.

Python must not generate HTML.

## 18. Astro responsibilities

Astro owns:

- loading the validated static JSON at build time;
- checking its TypeScript-compatible shape;
- page metadata and landmarks;
- accessible caption, headers, units, empty state, and table markup;
- summary presentation;
- static detail disclosure;
- value and label formatting;
- responsive local overflow;
- static route generation.

Astro must not load GeoJSON or recalculate domain totals for the production Statistics page.

## 19. Browser responsibilities

The initial migrated Statistics page should use zero custom browser-side JavaScript.

Accessible record details can use native HTML disclosure. The browser provides only native scrolling, focus, and disclosure interaction. Client sorting, filtering, Tippy, Popper, and runtime data fetching are not required by current behavior.

If later research proves interactive filtering essential, it must be introduced as a separate progressive-enhancement decision.

## 20. Accessibility contract

The future page must provide:

- one descriptive H1;
- a summary before the detailed table;
- a table caption;
- named row and column headers with `scope`;
- explicit GOT units;
- keyboard-operable details;
- focus visibility;
- numbers in addition to color bands;
- local table overflow without page overflow;
- a scroll affordance;
- a meaningful valid-empty-dataset state;
- no runtime loading state.

## 21. Responsive contract

Use a separate summary plus a horizontally scrollable detailed table. Preserve all year columns rather than hiding history. Prefer a sticky period column and sticky column headers if testing confirms they do not obscure focus or content.

Do not replace the dataset with 524 stacked cards. Do not rely on horizontal page scrolling.

## 22. Backward compatibility

During implementation:

- `/legacy/statistics/index.html` remains available;
- it continues using the unchanged Expeditions GeoJSON;
- `/statistics/` is introduced only after the static page passes parity and accessibility checks;
- navigation switches only when the new page is approved;
- deployment redirects are deferred to Netlify configuration;
- the dedicated JSON does not replace or mutate the legacy GeoJSON.

## 23. Migration stages

1. Sprint 10: audit, proposed types, read-only source validator.
2. Sprint 11: Python generator, dedicated JSON, production contract validation.
3. Later Statistics page sprint: Astro route and semantic static presentation.
4. Parity verification and navigation switch.
5. Deployment redirect decision after the native route is stable.

## SPRINT 11 — Statistics Static Data Generation

### Scope

- Implement a Python generator for `src/data/generated/statistics.json`.
- Keep `website/old-site/expeditions/expeditions.geojson` unchanged.
- Emit schema version 1 matching `StatisticsDataset`.
- Normalize exactly `nr`, `date`, `name`, and `got`.
- Generate records, 36-period yearly series, record references, and summaries.
- Use deterministic sorting and stable UTF-8 JSON serialization.
- Validate required fields, types, dates, IDs, period membership, totals, references, and null policy.
- Add fixtures or deterministic assertions for empty data, invalid date, duplicate ID, invalid GOT, equal-date ordering, year boundaries, period boundaries, and future periods.
- Add a Node or Astro-side validator for the generated JSON contract.
- Keep the integration boundary at a static JSON import; do not create the `/statistics/` Astro page yet unless Sprint 11 is explicitly expanded.
- Do not alter Leaflet, map behavior, or the current legacy route.

### Acceptance criteria

- generator exits successfully for the current 524 valid records;
- output path is `src/data/generated/statistics.json`;
- output is deterministic for identical source and generation date;
- all 524 records appear once;
- every record ID is unique and referenced by exactly one period;
- all yearly and global totals reproduce audited values;
- every year has 36 ordered periods;
- only future periods use null cumulative values;
- generated JSON passes contract validation;
- current GeoJSON checksum and legacy Statistics behavior remain unchanged;
- normal Astro development and build remain successful.
